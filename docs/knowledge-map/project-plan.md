# 数据工程知识地图建设任务书

## 目标

为数据开发、数仓和数据工程求职建立一张可持续维护的学习地图。学习者可以从真实岗位或工程问题进入，看见工作全貌、先修知识、材料和独立验收方式。保留计算机基础、AI 发展、agent 和可靠使用模型的路径。Sprint 是从地图中选出的一条面试训练路线。

地图允许标注缺口。一个节点只有在来源和要求深度明确、学习材料可定位、检验可复做后，才记为已覆盖。学习者是否掌握，另以独立操作或解释记录为准。

## 可复用的基线

- [已有岗位统计](../../research/jd-stats.md)与[后续岗位汇总](../../research/targets-summary.md)使用各自的日期、样本和分母。
- [面经统计](../../research/mianjing-stats.md)提供面试观察，和岗位原文分别记录。
- [课程大纲](../syllabus.md)、[学习流程](../learning-path.md)、[数据工程全景](../notes/m0-overview.md)提供现有课程和练习入口。
- [订单验收样例](order-metrics.md)演示一条岗位要求怎样接到 SQL、建模和 AI 输出验证。

## 方法论与扩展条件

1. **先定义能力，再判覆盖。** 岗位原文提供需求证据。课程和工程案例补充先修及练习；推导关系显式记录。每项能力分别核对原文、教学目标和可执行验收。
2. **先做能被推翻的小样。** 从一个已收录 JD 映射到现有本地练习，用另一条隔离样本检查映射能否迁移。AI 历史用原始资料核对时序和因果主张，工程验证用能让错误答案通过表面检查的反例。三个方向各留一个可查结果。
3. **小样达到门槛才扩大。** 岗位条款能逐项定位，关键硬要求没有被合并丢失，练习经独立实跑能拒绝已知反例，才扩大相应批次。发现系统性漏项时回改模板和依赖，保留前后结果。
4. **先审计划。** 用[独立审阅提示词](plan-review-prompt.md)收集反例与修订建议。建设工单在计划确认后安排。

## 工单与依赖

| 工单 | 输入与边界 | 交付及验收 | 依赖 |
| --- | --- | --- | --- |
| M01 核对旧岗位样本 | 仓库两版岗位材料，按岗位和公司识别重复 | 输出编号、来源、观察日期、岗位归类和当前可核状态。说明各样本与旧统计的关系 | 无 |
| M02 采集留出岗位 | 官网招聘页，按方向采集新增样本 | 留出一批建图时未见的岗位。逐条保存可公开引用的定位，区分关闭、可访问和在招 | 无 |
| M03 岗位要求映射 | 先完成一个试点，再使用 M01 的样本 | 逐条保存原文位置。拆分复合条款，保留硬要求、职责、加分和任选，标明原文深度及推导先修。能据原文追查覆盖 | M01 |
| M04 数据工程主题与材料 | 数据生命周期、现有 Sprint、课程、教材和官方文档 | 给 SQL、建模、Python、管道、调度、质量和分布式计算建立学习节点。每项至少定位到一段材料和一种检验 | M03 |
| M05 计算机基础和工程先修 | CS50、数据库课程及各概念的原始资料 | 从 CSV 编码、索引、事务、网络和进程等真实问题切入。写清前置与应用关系，逐项定位讲次或章节 | 无 |
| M06 AI 史和 agent | 原始论文、作者讲义及工程文档 | 写出关键技术当时要解决的问题、局限和替代路线。从现有模型概览接到检索、工具调用、执行反馈与评估 | 无 |
| M07 模型与代码的验证案例 | 现有 SQL 合成样例及后续 Python、数据管道案例 | 每例公开输入、独立预期、实测输出和失败条件；加入至少一种“输出看似正确”的反例 | 无 |
| M08 学习入口与长视频链接 | 已验收的地图节点和现有长视频资料 | 通过当前任务进入总图。每段材料写明切入问题、要看的范围和看完能做什么。初学顺序与时间线分别标注 | M04–M07 |
| M09 留出验收与发布 | 留出 JD、未见变式、各路径的来源记录 | 按岗位逐条对照，未覆盖的关键要求列出而非并入频率；复跑案例，核对引用、链接及待补项 | M02、M08 |

M01、M02 和 M05–M07 可以并行。先完成 M03 一个可验样例，再扩大岗位映射。每次派发明确到一项输出，给不同执行者划定文件范围。模型适合起草和提出反例，验收依靠原文、可复做的结果和独立复核。

### 一个节点的交付样式

- **出处**：官方岗位编号和条款定位，或技术原文的版本、章节和日期。
- **学习目标**：能观察的行为和目标深度，如“能逐订单说明 JOIN 为什么改变汇总”。
- **关系**：先学什么、在哪个场景用、与哪个历史变化有关。
- **学习方式**：指定讲次、文档或书章，说明适合看演示、读原文、陪练还是做项目。
- **验证**：写明输入、独立预期及失败判据，只有实际运行并比对的结果标为已验证。

## GitHub 协作约定

1. 用 [GitHub Issues](https://github.com/johnnyzhang-eng/data-engineering-20day-sprint/issues)记录任务、认领、阻塞和验收。认领时说明工单号及将改动的目录，先读原讨论。
2. 提交只包含对应改动。PR 关联工单，并写明来源、复现方式、已验证结果、待核事项。相关原始材料不得包含凭证、私人身份资料或未经授权的公司材料。
3. 模型协作公开记录任务版本、模型标签、结果状态、可引用的证据和采纳理由。调用超时、权限未核、HTTP 错误与内容验收各自记录。公开记录不需要附上账号材料或内部逐字对话。
4. 当前依据和核验结果见[建设回执](verification-log.md)。后续变更优先进与工单关联的 PR，并更新相应证据。
