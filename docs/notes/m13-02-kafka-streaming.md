# M13：Kafka 与流处理入门——事件怎样分发与计算

> 本讲只要求能说清 Kafka、Flink 是什么，以及事件流与定时批量同步有什么不同。用一条虚构订单变化，串起“捕获 → 传输 → 计算 → 落地”即可。

## 1. Kafka 管事件的保存与分发

Kafka 是分布式事件日志与流平台：生产者写入事件，消费者按需读取。数据库变更捕获负责产生增改删事件；Kafka 保存、分发事件，聚合与结果更新由消费者或流处理应用完成，Kafka 生态也提供 Kafka Streams 等计算能力。

- **Topic（主题）**：按用途组织的事件流，如订单变更；一份事件可供多个下游读取。
- **Partition（分区）**：Topic 内可并行读写的日志单元，只保证分区内写入顺序；按 key（标识实体的键，如订单号）分区且映射规则不变时，同键事件可保持在同一分区。
- **消费者组**：多个消费者共同分担订阅；传统组内同一时刻一个分区只交给一个消费者，不同组各自维护进度。
- **Offset（偏移量）**：事件在某个分区里的位置，不是全 Topic 的统一序号；提交进度表示失败恢复后从哪个位置继续读。

数仓和监控可使用不同组独立读取订单流；同组只有四个分区时，六个消费者通常最多四个获得分区。加分区可能改变键映射，热点订单键也仍可能拖慢一个分区，不能只靠增加消费者解决。

## 2. 能重放，不等于结果只写一次

先提交进度再写结果，崩溃可能漏写；先写结果再提交，崩溃可能重复读取。因此常见方案是允许至少一次处理，再让下游幂等：同一事件重复处理，最终业务结果与处理一次相同。

例如按事件标识去重，或按业务键与可靠版本取最新完整状态。去重记录与结果若分属两个系统，仍要分析中途失败；“消费进度已提交”不能证明外部结果正确。重放还受日志保留期限约束，不能假定任意历史都能重读。

## 3. Flink 是什么，和 Spark 批处理有什么不同

Flink 是分布式数据处理引擎，能持续接收事件并维护状态，例如保存各订单最新状态，随支付、退款事件更新十分钟成交额。状态就是计算跨事件保留的中间信息，运行时要管理其恢复与增长。

Spark 批处理常针对有界输入，例如固定昨天的订单，完成扫描、关联和聚合后结束；持续流任务则通常没有预设结束点，需要处理乱序、迟到和长期恢复。**Flink 和 Spark 现在都支持批与流**：Flink 可处理有界数据，Spark 的 Structured Streaming 也能持续增量计算，默认常采用微批，即把流分成连续的小批次。选择要看延迟、状态、已有生态与运维成本，不能套用“Flink 只能流、Spark 只能批”。

Watermark 是按事件时间（业务实际发生时间）推进窗口的进度估计，不保证更早事件永不迟到；Checkpoint 是保存计算状态和输入进度、供故障恢复的一致性快照。两者分别回答“窗口等到哪里”和“失败从哪里恢复”，外部结果是否只写一次还依赖连接器及提交协议，本讲不展开配置。

## 4. 怎样与定时同步比较

按更新时间定时扫表，是每轮选一个范围再构建、校验、发布；事件流则持续读取变化，维护各分区进度和计算状态。分页游标不是 Kafka offset，批次回看窗口也不是事件时间进度机制。可分别说明触发频率、恢复位置、删除传播、重复处理四点，再判断是否需要流处理；引入 Kafka 不会补出生产者漏发的删除。
