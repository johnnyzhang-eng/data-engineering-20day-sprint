# 学习任务清单：20 天要学的全部内容

这份清单把计划里的 13 个模块拆成具体的知识点，每个知识点就是一项任务。

**勾选规则**：只有在面试条件下（无 AI、无文档、限时）独立做对，并且能讲清"原理"那一问，才打勾。看过讲义、跟着示范做对，都不算。勾选的依据记在 `daily/` 的当天记录里。

**为什么每项都配一个"原理"问题**：做过项目，能讲出"我是怎么做的"，面试官接着问"为什么这样做""换个条件会怎样"时就答不上来，这正是要补的地方。所以每个知识点除了"会写、会用"，还要求能回答一个原理问题。

**依据**：模块和时间按 37 篇数据开发面经、17 份公开 JD 的统计来定（见 [`research/`](../research/)）。括号里的 `x/37` 表示 37 篇面经里有几篇考到。

## 学习顺序：从零开始

先看全貌，再学工具，再学原理，最后串起来。后一步依赖前一步：

0. **全景**（准备阶段 10/30）：数据工程是做什么的；一条订单数据从产生到出现在报表上，要经过哪些环节；13 个模块各在哪个环节。先有地图，后面学的每个知识点都知道该放在哪。
1. **SQL 基础**（M1，D1–D2）：每个环节都用 SQL 读写数据，后面所有内容都要用到它。
2. **数仓建模**（M3，D2–D6 下午）：和 SQL 并行学。建模解释了"表为什么长这样"，SQL 才不只是语法。D3 上午学 JOIN 的行数放大、下午学粒度，这是同一个问题的两面。
3. **SQL 进阶**（M2，D3–D7）：JOIN、窗口函数，建立在 M1 之上。
4. **Python**（M9，D4 起每天少量）：SQL 过了 D3 门槛才加，避免两门语言同时从零开始。
5. **ClickHouse**（M6，D6）：学完建模，再看一个具体的数据库怎样存这些表。
6. **Spark / Hive / HDFS**（M5，D8–D9）：数据大到一台机器放不下时，怎么存、怎么算。
7. **ETL 幂等与数据质量**（M7，D9）：知道数据怎么流动之后，再学流动出错时怎么办。
8. **场景题**（M4，D10–D11）：数据倾斜要先懂 Shuffle，所以排在 M5 之后。
9. **算法、数据库原理、CDC/Kafka/Flink**（M10、M12、M13，D11–D13）：面试里占比小，放在主线之后。
10. **行为面与 HR 面**（M11，D14）。**项目防守**（M8）贯穿全程：每学完一块，就回到自己的项目上再讲一遍。

每个知识点内部也按同一个顺序学：它为什么存在 → 解决什么问题 → 怎么做 → 什么时候不适用。

## M1 SQL 基础（单表 30/37 篇考到 SQL）

- [ ] **SELECT、WHERE、ORDER BY、LIMIT、DISTINCT**
  原理：SQL 的逻辑执行顺序是 FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT。为什么 WHERE 里不能用 SELECT 里起的别名？
- [ ] **NULL 的三值逻辑**
  原理：`NULL = NULL` 为什么不是 true？`NOT IN (子查询)` 里只要有一个 NULL，为什么结果会变空？
- [ ] **COUNT(\*)、COUNT(列)、COUNT(DISTINCT 列)、SUM、AVG**
  原理：每个函数的分母是什么？AVG 为什么会忽略 NULL，什么时候这会让结果偏高？
- [ ] **GROUP BY 与 HAVING**
  原理：WHERE 在分组前过滤，HAVING 在分组后过滤。为什么 SELECT 里只能出现分组列或聚合结果？
- [ ] **CASE WHEN 与条件聚合**
  原理：`SUM(CASE WHEN … THEN 1 ELSE 0 END)` 为什么能在一次扫描里算出多个指标？
- [ ] **常用日期、字符串函数**
  原理：不同数据库（SQLite、MySQL、Hive）的函数名不一样，面试时先说明自己用的是哪种方言。

## M2 SQL 进阶（连续登录 8/37，分组最大值对应记录 2/37，累计值 2/37）

- [ ] **INNER、LEFT、FULL JOIN；条件写在 ON 和写在 WHERE 的区别**
  原理：LEFT JOIN 时把右表的条件写进 WHERE，为什么会变成 INNER JOIN 的效果？
- [ ] **JOIN 的行数放大**
  原理：一对多、多对多连接后行数怎么算？为什么"先聚合再连接"能避免金额被重复累加？
- [ ] **子查询、CTE（WITH）、IN 与 EXISTS**
  原理：相关子查询每行都要执行一次。CTE 解决的主要是可读性问题。
- [ ] **窗口函数基础：`OVER (PARTITION BY … ORDER BY …)`**
  原理：窗口函数为什么不减少行数？它和 GROUP BY 的本质区别是什么？
- [ ] **ROW_NUMBER、RANK、DENSE_RANK → 分组 TopN**
  原理：有并列时三者的结果分别是什么？为什么 TopN 必须在外层查询过滤，不能直接写在 WHERE 里？（窗口函数在 WHERE 之后才计算）
- [ ] **LAG、LEAD：环比、相邻两行的差**
- [ ] **累计值与移动窗口：`SUM() OVER (ORDER BY … ROWS BETWEEN …)`**
  原理：加了 ORDER BY 后默认的窗口范围是什么？ROWS 和 RANGE 遇到同一天有多行时，结果有什么不同？
- [ ] **连续登录 N 天**
  原理：为什么"日期减去行号"后，连续的日期会得到同一个值，可以当分组标识？
- [ ] **留存率**
  原理：次日留存的分子、分母分别是什么？同一用户一天登录多次时，为什么要先去重？
- [ ] **行列转换**
  原理：行转列用条件聚合；列转行用 UNION ALL（Hive 里用 explode）。
- [ ] **速度**：D7 每题 ≤15 分钟 → D14 每题 ≤10 分钟 → D17 每题 ≤7 分钟

- [ ] **数仓是什么，和业务数据库有什么不同**
  原理：业务库为交易服务（频繁增删改、只要当前状态）；数仓为分析服务（读多写少、保留历史、面向主题）。
- [ ] **分层：ODS、DWD、DWS、ADS，以及维度层 DIM**
  原理：为什么要分层？（复用、隔离源系统的变化、出了问题能逐层定位）不分层会出现什么问题？
- [ ] **事实表与维度表**
  原理：事实表记录"发生了什么"和可度量的数字；维度表描述"从什么角度看"。
- [ ] **粒度（4/37）**
  原理：为什么建表前要先声明"一行代表什么"？粒度混在一起会怎样导致重复计算？
- [ ] **事实表的三种类型：事务事实表、周期快照事实表、累积快照事实表**
- [ ] **星型模型与雪花模型**
  原理：星型模型用冗余换取更少的 JOIN、更快的查询；雪花模型更规范，但 JOIN 更多。数仓里为什么通常选星型？
- [ ] **主题域划分（4/37）、维度退化（3/37）**
- [ ] **缓慢变化维 SCD1、SCD2、SCD3，拉链表（3/37）**
  原理：拉链表用开始日期、结束日期两列记录历史。查"某一天的状态"怎么写？为什么比每天存一份全量快照省空间？
- [ ] **全量同步与增量同步**
  原理：增量同步靠什么识别哪些数据变了（更新时间、自增 ID、CDC）？源头删除了数据怎么处理？
- [ ] **数仓质量怎么评价（3/37）**：完整性、准确性、一致性、及时性、唯一性

## M4 场景题（场景设计 31/37，数据倾斜 16/37）

- [ ] **数据倾斜的现象与定位**
  原理：同一个 key 的数据都会被 Shuffle 到同一个分区，热点 key 就让少数几个 task 特别慢。怎样从 task 耗时和 key 的分布确认是倾斜？
- [ ] **倾斜的处理方法及各自适用的条件**
  - 加随机前缀打散，两阶段聚合（适合聚合类）
  - 小表广播 / map join（适合大表连小表）
  - 热点 key 单独处理；空值 key 先过滤或打散
- [ ] **慢任务排查思路**：先找到最慢的 Stage，再看数据量、倾斜、资源、小文件
- [ ] **小文件问题**
  原理：小文件为什么会给 NameNode 带来压力，又为什么会让 task 数量暴增？怎么合并？

## M5 Spark / Hive / HDFS（Spark 18/37，Hive 10/37，宽窄依赖 5/37，HDFS 读写 4/37）

- [ ] **HDFS：NameNode、DataNode、块、副本；读写流程**
  原理：文件为什么要切成块？为什么默认 3 个副本？
- [ ] **MapReduce 的思路：Map → Shuffle → Reduce**
- [ ] **Hive：SQL 怎样变成分布式作业；内部表与外部表；分区与分桶**
  原理：分区裁剪为什么能让查询变快？
- [ ] **列式存储 Parquet、ORC**
  原理：分析查询只读需要的列，同一列数据类型相同、压缩率高。
- [ ] **Spark 架构：Driver、Executor；Job、Stage、Task**
- [ ] **RDD 与 DataFrame；惰性求值（transformation 与 action）**
- [ ] **宽依赖与窄依赖**
  原理：为什么 Stage 恰好在宽依赖（需要 Shuffle）的地方切开？
- [ ] **一条 GROUP BY 在 Spark 里的完整执行过程**（本模块出口题）
- [ ] **Spark 为什么比 MapReduce 快**：中间结果放内存、DAG 调度

## M6 ClickHouse MergeTree（简历上的项目用到）

- [ ] **ClickHouse 的定位：列式 OLAP 数据库**
- [ ] **MergeTree：分区、排序键、稀疏主键索引**
  原理：排序键决定数据在磁盘上的顺序。稀疏索引为什么能用很小的空间跳过大量数据？
- [ ] **后台合并（merge）**
  原理：每次写入先形成一个小的数据片段（part），后台再异步合并。
- [ ] **ReplacingMergeTree 与版本列**
  原理：去重只在合并时发生，所以合并完成前查询可能看到重复数据。
- [ ] **查询时去重：FINAL、argMax、GROUP BY**，以及各自的代价

## M7 ETL 幂等、重跑与数据质量（简历上的项目用到；面经中有回滚、质量相关题）

- [ ] **幂等是什么**：同一批数据跑一次和跑多次，结果一样
- [ ] **覆盖写与追加写**
  原理：为什么按分区覆盖写（INSERT OVERWRITE）天然是幂等的，追加写却会重复？
- [ ] **写到一半失败怎么办**
  原理：先写临时表或临时分区，校验通过后再原子切换（rename、交换分区），这样不会出现空表或半截数据。
- [ ] **回滚、重跑、补数**：按分区回溯
- [ ] **数据质量校验（DQC）规则**：行数波动、主键唯一、空值率、枚举值、上下游对账；强规则阻断任务，弱规则只告警
