# 技能、工具和模型分工

这些办法对应[建设任务书](project-plan.md)。是否启用某个 skill 取决于工单和实际运行环境。

| 场景 | 已有技能或工具 | 可核对的产物 |
| --- | --- | --- |
| 岗位和技术资料核对（M01、M02、M04–M06） | gh、网页检索、官网招聘页、原论文或官方文档。用 Python 辅助去重和版本对账 | 来源、日期、原文定位、快照有无、分类与待核项 |
| 教学和练习验证（M03–M08） | 现有题库与讲义、VS Code、SQLite、Python 标准库。本人先预测或作答，AI 对照结果反馈 | 独立预期、实测输出、拒绝错答的反例与本人操作证据 |
| Codex CLI、子代理和权限问题 | openai-docs 核对 Codex 行为。其它模型平台看各自官方文档和实际运行回执 | 入口、模型、能用的工具、权限和失败阶段 |
| 交互图与初学导航（M08） | visualize:visualize 适合试验先修图、数据流和学习入口。GitHub 保留 Markdown | 一个能导航到实际材料、练习和下一步的视图，与源节点同步 |
| 有稳定的重复工单后 | skill-creator 可封装经多批验证的 JD 抽取与核验流程 | 明确输入、可运行小样、错误示例和停止条件 |
| 长对话或阶段交接 | chat-handoff 保存增量、本人理解、实际运用与未决问题 | GitHub 记录公开成果和验收，私人记录本地保留 |

## 模型分工

- Codex 负责派单、原文和来源核验、实跑与归并。Opus 和 Kimi 独立审查重大设计，讨论可核对的分歧。本人确认取舍与启动时点。
- Magpie 的已核实路由可以处理批量抽取、来源定位、材料草稿及反例候选。每次派发限制输入和输出范围。分别核实模型、工具、权限、成本和终答，再做内容验收。
- 首轮复核用真实岗位、原论文和 SQLite/Python 结果裁决。若两方对关键问题仍有明确分歧，再让第三个模型审同一证据包。
- 操作用 Ghostty。凭证由本人管理的客户端或安全存储提供。GitHub 记录可追溯的方案、尝试、结果和失败状态，公开内容须为授权公开资料或合成数据。

## GitHub 留痕

每项工单在关联 Issue 或 PR 写明输入版本、公开来源、执行者与复核者、改动范围、模型草稿、独立预期和实际证据、未验项、采纳理由及下一步。公开提交只包含工单相关改动，提交前运行仓库检查。材料不足、试跑失败和对结果的不同判断也保留记录。
